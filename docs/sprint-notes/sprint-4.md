## Learning objectives

By the end of this chapter you should be able to explain **why schema versioning matters**, distinguish Flyway baselining from executing V1, configure PostgreSQL and H2 safely, describe Spring proxy-based transaction boundaries and rollback, reason about JPA flush/commit, diagnose lazy/eager fetching and N+1 behavior, explain OSIV, and translate database constraint failures into safe API errors.

## 1. Starting architecture and why Sprint 4 mattered

Sprints 1–3 produced Employee and Department REST APIs, JPA relationships, pagination and search. A functioning application is not yet a reliably evolving application. Imagine adding a column next month: one developer's database may contain it, another's may not, and a deployment might change the schema without review. Similarly, a multi-step service operation can partially succeed if transaction boundaries are unclear. Sprint 4 addresses those engineering risks.

```text
Postman / HTTP client
       ↓
Spring MVC Controller — input, HTTP semantics
       ↓
Spring Service — business rules, @Transactional boundary
       ↓
Spring Data JPA Repository
       ↓
Hibernate ORM — entity state, SQL generation, flush
       ↓
JDBC / HikariCP → PostgreSQL — schema, FK/unique constraints, commit

Flyway → applies versioned schema changes BEFORE Hibernate validates mappings
```

**Responsibilities:** Flyway evolves schema; JPA describes Java-to-table mapping; Hibernate implements ORM behavior; PostgreSQL stores data and enforces constraints. None substitutes for the others.

## 2. Flyway fundamentals — from manual changes to repeatable migrations

### 2.1 The problem with ad hoc DDL

Suppose a teammate executes `ALTER TABLE employees ADD COLUMN ...` manually. Their database works, but no source-controlled record explains the change. On another machine the application fails. With versioned migrations, the SQL lives alongside code and the database records which changes were applied.

### 2.2 Flyway naming and ordering

```text
src/main/resources/db/migration/
  V1__initial_schema.sql
  V2__employee_lifecycle.sql       # introduced in Sprint 5, NOT Sprint 4
```

A conventional versioned name is `V<version>__<description>.sql`. The two underscores separate version and description. Flyway discovers migration files, checks migration history, and applies pending versions in order. In Sprint 4, V1 was the initial schema migration; the actual V2 was implemented later.

### 2.3 Dependencies — project implementation

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-flyway</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

The starter integrates Flyway with Spring Boot startup. The PostgreSQL module provides database-specific support. Spring Boot dependency management supplies compatible versions; the dependencies still need to be declared.

### 2.4 What V1 represented

The Sprint 4 V1 script reproduces the **preexisting** schema from Sprints 1–3: `departments`, `employees`, identity primary keys, the unique email constraint `uk_employees_email`, and employee→department FK `fkgy4qe3dnqrm3ktd76sxp7n4c2`. The historical schema allowed nullable department name and nullable employee name/email/department columns. **Do not invent stricter V1 constraints in documentation:** the goal was to represent the real existing schema.

**Illustrative simplified DDL, not the verbatim project V1 file:**

```sql
CREATE TABLE departments (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(255)
);
CREATE TABLE employees (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    first_name VARCHAR(255),
    last_name VARCHAR(255),
    email VARCHAR(255),
    department_id BIGINT,
    CONSTRAINT uk_employees_email UNIQUE (email),
    CONSTRAINT fk_employee_department FOREIGN KEY (department_id)
        REFERENCES departments(id)
);
```

The actual project FK name differs; consult `V1__initial_schema.sql` for exact SQL. The simplified example exists to explain PK, FK, uniqueness and nullability.

### 2.5 `flyway_schema_history` — the migration ledger

The table records versions, descriptions, migration types, checksums where applicable, installation order and success. The presence of a row is **not** proof that a particular SQL file ran: a **BASELINE** entry means the schema was declared to already exist at that version.

```sql
SELECT installed_rank, version, description, type, success
FROM flyway_schema_history
ORDER BY installed_rank;
```

**Sprint 4 observed difference:**

| Database | History at V1 | Meaning |
|---|---|---|
| Existing `nexus` | Version 1 `<< Flyway Baseline >>` | Existing tables were adopted into Flyway tracking; V1 SQL was **not** run there |
| Empty `nexus_flyway_test` | Version 1 `initial schema`, type SQL | Flyway actually created the schema from V1 |

This distinction is essential for explaining a migration audit or debugging why two environments have different histories.

### 2.6 Baselining safely

An existing database already contains tables. Running `CREATE TABLE` from V1 again could fail or damage a poorly designed migration process. Sprint 4 **temporarily** used `spring.flyway.baseline-on-migrate=true` to establish version 1 on `nexus`, then returned it to `false`.

```properties
spring.flyway.enabled=true
spring.flyway.locations=classpath:db/migration
spring.flyway.baseline-on-migrate=false
spring.flyway.baseline-version=1
spring.flyway.validate-on-migrate=true
spring.jpa.hibernate.ddl-auto=validate
```

**Why turn automatic baselining off?** If the application accidentally points at a populated but unmanaged database, silently declaring it at version 1 could conceal a wrong datasource or incompatible schema. An intentional one-time baseline is safer than a permanent automatic setting.

### 2.7 Flyway versus `ddl-auto`

| Hibernate setting | Meaning | Suitability |
|---|---|---|
| `create` | Recreate schema on startup | Disposable tests only |
| `create-drop` | Create and drop around test lifecycle | Isolated H2 tests |
| `update` | Attempt implicit schema modifications | Avoid as schema change strategy |
| `validate` | Check mapping against schema; do not create missing tables | Sprint 4 dev/prod direction |
| `none` | No Hibernate schema action | Useful when validation is managed separately |

**Mental model:** Flyway changes database shape; Hibernate `validate` checks that the current entity mappings can use it. If validation fails, investigate schema/mapping mismatch rather than switching to `update` to hide the issue.

### 2.8 Why applied migrations are immutable

Flyway checks migration integrity. Editing a previously applied version can create checksum validation errors and breaks reproducibility. To add a field, write V2; to change it again, write V3. Never rewrite an applied V1 or V2 to make an existing database 'match' a new model.

### 2.9 Sprint 4 verification

The empty `nexus_flyway_test` database executed V1, produced the three expected tables and passed Hibernate validation. The populated `nexus` database was baselined at V1 while preserving existing records. Sprint 4 discussed a hypothetical joining-date V2, but **did not implement V2**. Sprint 5 later implemented the real V2 with both joining date and employment status.

## 3. Environment isolation: dev/prod/test and secret handling

### 3.1 Why tests must not depend on your workstation database

A unit/integration test should be repeatable and should not unexpectedly write to the developer's real PostgreSQL database. If the test accidentally uses the `dev` profile, it can require local credentials, encounter different schema state, or trigger migrations on the wrong datasource.

### 3.2 Sprint 4 test profile — project configuration

```properties
# src/test/resources/application-test.properties
spring.datasource.url=jdbc:h2:mem:nexus_test;DB_CLOSE_DELAY=-1
spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=
spring.jpa.hibernate.ddl-auto=create-drop
spring.flyway.enabled=false
spring.jpa.show-sql=false
spring.jpa.open-in-view=false
```

`jdbc:h2:mem:` selects an in-memory database; `create-drop` makes the schema disposable; disabling Flyway avoids attempting PostgreSQL-specific migration SQL in H2. `@ActiveProfiles("test")` tells a Spring test which configuration to load.

```java
// Illustrative annotation placement
@SpringBootTest
@ActiveProfiles("test")
class EmployeeServiceApplicationTests {
    // Spring context loads using isolated H2 configuration
}
```

**Important boundary:** H2 tests verify many JPA behaviors but not PostgreSQL-specific DDL, locking, constraints, or optimizer behavior. The scratch PostgreSQL V1 migration test complements them.

### 3.3 External secrets

The established project configuration uses an environment variable rather than committing the database password:

```properties
spring.datasource.password=${DB_PASSWORD}
```

Tests should not require `DB_PASSWORD`. Sprint 4 verified the suite with database environment variables removed from the terminal. Never copy real passwords into notes, examples or Git.

### 3.4 Profile precedence

`application.properties` provides defaults; `application-dev.properties` and `application-test.properties` add profile-specific values; command-line properties can override defaults for a single run. A test profile is not merely a naming convention—it changes the datasource and migration behavior. Always inspect startup logs for the **actual JDBC URL and active profile** before allowing a migration.

## 4. Transactions: a business operation should succeed or fail together

### 4.1 What is a transaction?

A database transaction groups operations into one unit of work. If a method creates a department and performs additional dependent updates, partial persistence may leave inconsistent state if an error occurs midway. A transaction provides a commit point and a rollback path.

### 4.2 ACID in project language

- **Atomicity:** either the entire transaction commits or none of its changes become committed.
- **Consistency:** committed changes must satisfy enforced constraints; application invariants also require correct logic.
- **Isolation:** concurrent transactions interact under the configured isolation level; it does **not** mean they never affect each other.
- **Durability:** committed data survives a database failure within the database's durability guarantees.

### 4.3 Service-layer boundaries — project implementation

Sprint 4 applied `@Transactional` to Employee and Department write methods and `@Transactional(readOnly = true)` to read methods. A service can coordinate multiple repository calls; the transaction should encompass the **business operation**, not just one repository call.

```java
// Illustrative pattern reflecting the Sprint 4 service design
@Service
public class DepartmentService {
    private final DepartmentRepository departmentRepository;
    private final EmployeeRepository employeeRepository;

    public DepartmentService(DepartmentRepository departments,
                             EmployeeRepository employees) {
        this.departmentRepository = departments;
        this.employeeRepository = employees;
    }

    @Transactional
    public void deleteDepartment(Long id) {
        Department department = departmentRepository.findById(id)
            .orElseThrow(() -> new DepartmentNotFoundException(id));
        if (employeeRepository.existsByDepartmentId(id)) {
            throw new DepartmentHasEmployeesException(id);
        }
        departmentRepository.delete(department);
    }
}
```

The business check gives a meaningful 409 for occupied departments. PostgreSQL's foreign key still protects referential integrity if another transaction assigns an employee concurrently.

### 4.4 How `@Transactional` works

In the usual Spring proxy-based setup, another Spring bean calls a **proxy** around the service. The proxy opens or joins a transaction, invokes the target method, then commits or rolls back. Merely adding `@Service` does not automatically make every method transactional.

```text
Controller → Spring transaction proxy → begin/join transaction
                                  → EmployeeService.method()
                                  → repositories / Hibernate
                                  → commit or rollback
```

**Self-invocation trap:** `this.someTransactionalMethod()` inside the same class bypasses the proxy in the typical proxy mode. Therefore the annotation on that internally invoked method may not create the transaction you expect.

### 4.5 Propagation and rollback defaults

`Propagation.REQUIRED` (the default) joins an existing transaction or starts one. By default, Spring rolls back for unchecked exceptions (`RuntimeException`) and `Error`; checked exceptions generally require explicit `rollbackFor` if rollback is desired. These are general Spring rules; Sprint 4 directly verified rollback for an `IllegalStateException`.

```java
// Illustrative, NOT an added Sprint 4 method
@Transactional(rollbackFor = IOException.class)
public void importEmployees() throws IOException {
    // Checked exception now requests rollback
}
```

### 4.6 `readOnly=true` is not an authorization rule

It communicates read intent to transaction/persistence infrastructure and may optimize flush behavior. It does not guarantee that SQL writes are impossible on every database/driver, and it does not replace authorization or code review. Mapping DTOs inside the read transaction also avoids relying on an open persistence context later in the web layer.

## 5. Entity state, dirty checking, flush, commit and rollback

### 5.1 Managed versus detached

A JPA entity loaded inside an active persistence context is **managed**. Hibernate tracks changes to managed fields (dirty checking) and can write SQL at flush time even if you do not explicitly call `save` again. A detached entity is no longer tracked by that persistence context.

### 5.2 `save`, `flush`, `commit` are different

| Operation | What it means | What it does **not** guarantee |
|---|---|---|
| `save(entity)` | Ask repository to persist/merge entity | Immediate SQL or committed data |
| `flush()` / `saveAndFlush()` | Synchronize pending persistence changes to DB in current transaction | Transaction committed |
| Transaction commit | Finalize transaction if successful | Protection against every future concurrent change |
| Rollback | Undo uncommitted transactional changes | Undo changes from already committed transactions |

**Illustrative sequence:**

```text
BEGIN
INSERT INTO departments ...   ← flushed to DB
throw IllegalStateException
ROLLBACK                      ← inserted row does not remain
```

### 5.3 The actual Sprint 4 rollback experiment

`DepartmentTransactionTest` used `@SpringBootTest`, `@ActiveProfiles("test")`, `TransactionTemplate` and `departmentRepository.saveAndFlush(...)`. The test flushed an INSERT, deliberately threw `IllegalStateException`, then verified that the department was absent after rollback. This is stronger than simply asserting that an exception was thrown: it checks database state after the transaction.

**Illustrative equivalent shape (not verbatim test source):**

```java
assertThrows(IllegalStateException.class, () ->
    transactionTemplate.executeWithoutResult(status -> {
        departmentRepository.saveAndFlush(new Department("Rollback Demo"));
        throw new IllegalStateException("Force rollback");
    })
);
assertFalse(departmentRepository.existsByNameIgnoreCase("Rollback Demo"));
```

The actual test should isolate the name/records so that a preexisting row cannot invalidate the assertion. Sprint 4 reported the focused test passing, and the suite grew from 21 to 22 tests.

### 5.4 Why logs can mislead

An SQL `DELETE` or `INSERT` appearing in logs does not automatically prove commit. Flush can happen before the transaction completes. That is why the Department deletion log was changed to **`Department deletion requested for id={}`** instead of claiming success before commit. For data correctness, verify committed database state or use transaction-aware events after commit.

## 6. Relationship fetching: eager, lazy and the N+1 problem

### 6.1 Sprint 3 relationship recap

`Employee.department` is the owning `@ManyToOne` side; `employees.department_id` is the FK. The response DTO returns `departmentId`, not a nested Department entity. JPA relationships are Java object references; SQL relationships are foreign keys.

### 6.2 Default eager fetching

The earlier mapping was:

```java
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;
```

JPA `@ManyToOne` defaults to `EAGER`. When loading employees, Hibernate may issue additional SQL to initialize related departments. EAGER does not guarantee a single SQL JOIN; the exact SQL depends on query shape and provider.

### 6.3 Sprint 4 change — project implementation

```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "department_id")
private Department department;
```

LAZY delays loading related entity data until needed. In Sprint 4, a particular employee-list request changed from an employee SELECT plus a department SELECT to just the employee SELECT. This was a **measured improvement for that request**, not a blanket proof of N+1 elimination.

### 6.4 Why `getDepartment().getId()` can avoid extra SQL

The Employee row already contains `department_id`. Hibernate often represents a lazy association as a proxy whose identifier is known without fetching the whole Department. Reading only the identifier can therefore avoid initialization. This is provider- and access-pattern-sensitive: reading `getDepartment().getName()` usually needs the actual Department row.

### 6.5 N+1 explained

Imagine retrieving 100 employees in one SQL query, then triggering one extra Department query per employee. You may get 1+100 SQL statements. If many employees share departments, Hibernate caching may reduce queries, but you should not rely on that to hide an inefficient access pattern.

```text
1 SELECT employees ...
N SELECT departments WHERE id=?
```

**Illustrative future optimization, not added in Sprint 4:** use a targeted fetch join or entity graph when a response genuinely needs department details. For an ID-only DTO, fetching whole departments can be unnecessary overhead.

### 6.6 How to diagnose rather than guess

1. Reproduce the same Postman request with the same data.
2. Inspect Hibernate SQL logs.
3. Count queries and identify whether each is required by business logic.
4. Change fetch strategy only when evidence supports it.
5. Repeat the identical request and compare.

Sprint 4 observed a filtered employee request with a department-existence COUNT followed by the filtered employee SELECT. **Those two queries are intentional**, because they distinguish nonexistent department (404) from existing department with no employees (200 empty page). They are not N+1.

## 7. Open Session in View (OSIV) and transaction boundaries

### 7.1 What OSIV does

With OSIV enabled, a persistence context can remain associated with the web request after service code finishes. This can make lazy entity access in controller/serialization appear to work, while hiding extra SQL and blurring where persistence work happens.

### 7.2 Sprint 4 configuration

```properties
spring.jpa.open-in-view=false
```

Set in development, production and test profiles. With OSIV disabled, mapping a DTO that needs a lazy association must happen inside a suitable transaction/persistence context, or be supplied by an explicit query.

### 7.3 Typical failure and fix

```text
Repository loads Employee
Service transaction ends
Controller tries employee.getDepartment().getName()
→ possible LazyInitializationException
```

**Correct approach:** identify which data the response needs and fetch/map it in the service transaction (or use a projection). Do not automatically re-enable OSIV. This sprint's existing response required `departmentId`, not department name.

## 8. Data integrity: business checks plus database constraints

### 8.1 Why both layers matter

The service checks whether a department has employees before deletion, enabling a clear domain-specific error. But two transactions can race:

```text
Transaction A: checks department has no employees
Transaction B: assigns an employee to that department
Transaction A: attempts DELETE
Database FK: rejects invalid delete
```

The database is the final line of defense. A transaction by itself does not eliminate this race. More advanced locking or isolation strategies could be added later if needed.

### 8.2 Spring exception translation

Spring's data-access abstraction can translate persistence errors into `DataIntegrityViolationException`. This can represent unique constraints, foreign keys, or other integrity problems; it is not specific to one domain rule.

### 8.3 Sprint 4 handler — project implementation

```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<Map<String, String>> handleDataIntegrityViolation(
        DataIntegrityViolationException ex) {
    Map<String, String> error = new HashMap<>();
    error.put("error", "Conflict");
    error.put("message",
        "The requested operation conflicts with existing database data.");
    return ResponseEntity.status(HttpStatus.CONFLICT).body(error);
}
```

The handler intentionally does not return SQL statements, constraint names, stack traces or DB driver details to clients. HTTP **409 Conflict** is a reasonable mapping for a request conflicting with current stored data; domain-specific handlers remain preferred when a known business conflict can be described clearly.

### 8.4 What was actually tested

`GlobalExceptionHandlerTest` directly invoked the handler with a simulated `DataIntegrityViolationException` and checked status 409 and both JSON fields. That proves the handler's direct response construction. It does **not** prove an actual concurrent PostgreSQL race, MVC exception routing, or all exception wrappers thrown during transaction commit.

## 10. Debugging playbook

**Flyway complains about migration checksum:** confirm which version was applied and whether an applied file was edited. Do not casually change history rows or disable validation. Add a new migration for a new schema change.

**Hibernate schema validation fails:** compare entity field/column mappings to the actual schema; inspect migration history and datasource URL. Avoid switching `ddl-auto` to `update` as a shortcut.

**Test unexpectedly asks for PostgreSQL password:** inspect `@ActiveProfiles`, test resources, and environment overrides. Ensure H2 is active and Flyway is disabled in the test profile.

**SQL appears but row does not persist:** distinguish flush from commit and inspect transaction rollback/exception path.

**LazyInitializationException:** verify where DTO mapping occurs and whether required associations were fetched within the transaction.

**Unexpected extra SQL:** compare the precise request and count SQL statements. An existence query is not automatically N+1.

**Integrity violation exposes internals:** use exception translation and controlled error responses; preserve detailed diagnostics in server logs, not HTTP JSON.

## 11. Interview practice — questions and answers

**Q1. Flyway versus Hibernate `ddl-auto=update`?** Flyway makes explicit versioned, reviewable changes with history. Hibernate `update` attempts automatic schema adjustment, which is not a substitute for deliberate migration planning.

**Q2. Why baseline the existing database but execute V1 on scratch?** The populated database already had schema/data, so baselining adopted it without recreating tables. Scratch verified that V1 independently builds the expected initial schema.

**Q3. Does `@Service` imply transactions?** No. Service methods need explicit transaction boundaries or another transactional caller; repository methods may have their own transaction behavior.

**Q4. Why can a flushed INSERT disappear?** Flush synchronizes SQL within the current transaction; rollback can undo it before commit.

**Q5. What is self-invocation?** A call to another method on `this` bypasses Spring's proxy in normal proxy-based AOP, so the callee's transaction annotation may not be intercepted.

**Q6. Does `@Transactional(readOnly=true)` prevent all writes?** No. It is an intent/optimization hint, not a universal database write prohibition.

**Q7. Why change `@ManyToOne` to LAZY?** Avoid loading related Department objects when the response only needs employee fields or department ID; confirm impact with SQL logs.

**Q8. Is every second SELECT an N+1 problem?** No. A legitimate department existence check plus employee query is two purposeful queries; N+1 is a query amplification pattern caused by repeated per-record access.

**Q9. Why disable OSIV?** To keep persistence work and lazy loading within deliberate service transactions instead of accidental web-layer access.

**Q10. Why keep FK constraints if service checks exist?** Concurrent requests or non-API writes can bypass/preempt the check; the database must enforce referential integrity.

- Schema evolution must be explicit and repeatable.
- Adopt old databases carefully; verify fresh builds independently.

## 3. Transactions and rollback
Service write operations (`createEmployee`, `updateEmployee`, `deleteEmployee`, `createDepartment`, `updateDepartment`, `deleteDepartment`) use `@Transactional`. Read operations (`getAllEmployees`, `getEmployeeById`, `searchEmployeesByFirstName`, `getDepartmentById`, `getAllDepartments`) use `@Transactional(readOnly = true)`.

A service method is **not automatically transactional** merely because it has `@Service`; many inherited Spring Data JPA repository operations have their own transaction behavior. Service-level transactions span the complete business operation and DTO mapping. `readOnly=true` is an optimization hint, not an access-control mechanism. Spring's proxy-based transaction interception generally applies when calls enter through the Spring proxy; self-invocation bypasses that interception. Default `REQUIRED` propagation joins an existing transaction or creates one.

The existing `deleteDepartment` method loads the department, checks `employeeRepository.existsByDepartmentId(id)`, raises `DepartmentHasEmployeesException` when occupied, otherwise calls `departmentRepository.delete(department)`. It is transactional. The log message was refined to `Department deletion requested for id={}` because SQL flushing or transaction commit may happen later.

Created `DepartmentTransactionTest`, using `@SpringBootTest`, `@ActiveProfiles("test")`, `TransactionTemplate`, and `departmentRepository.saveAndFlush(...)`. The test deliberately throws `IllegalStateException` after a database INSERT is flushed, then asserts the department is absent after rollback. This demonstrates that **flush is not commit**. ## 4. JPA relationship fetching and OSIV
Original `Employee.department` mapping used default eager fetching:
```java
@ManyToOne
@JoinColumn(name = "department_id")
private Department department;
```
One observed `GET /api/employees?page=0&size=20&sortBy=id&direction=asc` produced an employee SELECT followed by a department SELECT. Changed mapping to:
```java
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "department_id")
private Department department;
```
The repeated request then produced only the employee SELECT. The API maps `employee.getDepartment().getId()` to `departmentId`, which Hibernate can normally read without initializing the full proxy. This is an **observed improvement from two SELECTs to one**, not proof that every future query avoids N+1.

Configured `spring.jpa.open-in-view=false` in development, production, and test profiles. This prevents relying on the web-request scope to lazily load entities after the service transaction. Read-only service transactions cover repository access and DTO mapping. An unexpected `LazyInitializationException` should prompt review of transaction/fetch boundaries, not automatic re-enabling of OSIV.

Postman checks after changes:
- `GET /api/employees?page=0&size=20` → 200, one employee SELECT.
- `GET /api/employees/1` → 200, one employee SELECT.
- `GET /api/departments` → 200, one department SELECT.
- `GET /api/employees?departmentId=1` → 200, department existence COUNT then filtered employee SELECT.

The two queries for department filtering are intentional: the existence check distinguishes nonexistent departments (404) from valid departments with zero employees (200 empty result). They are not evidence of N+1.

## 5. Database integrity and error handling
PostgreSQL's employee-to-department foreign key protects referential integrity even if an application-level precheck races with another transaction. Service checks improve business error messages but do not replace database constraints or eliminate races. A database violation can surface as `DataIntegrityViolationException`.

Added to `GlobalExceptionHandler`:
```java
@ExceptionHandler(DataIntegrityViolationException.class)
public ResponseEntity<Map<String, String>> handleDataIntegrityViolation(
        DataIntegrityViolationException ex) {
    Map<String, String> error = new HashMap<>();
    error.put("error", "Conflict");
    error.put("message",
        "The requested operation conflicts with existing database data.");
    return ResponseEntity.status(HttpStatus.CONFLICT).body(error);
}
```
Import `org.springframework.dao.DataIntegrityViolationException`. Removed duplicate `Map`/`HashMap` imports. Existing specific business exception handlers remain unchanged. The generic response avoids exposing SQL or constraint internals; it does not distinguish every unique or foreign-key violation.

Created `GlobalExceptionHandlerTest` as a focused unit test that calls the handler with a simulated `DataIntegrityViolationException` and verifies HTTP 409 and both response fields. **This does not simulate a real PostgreSQL race or verify all possible transaction-commit exception wrappers.** Focused test: 1 passed. Full `mvn clean verify`: **23 passed, 0 failures, 0 errors, BUILD SUCCESS**, executable JAR built.

## 6. Key lessons and interview-ready rules
1. Use Flyway for versioned, reviewable schema changes; use Hibernate `validate` rather than uncontrolled production schema updates.
2. Baseline existing populated databases; run initial migrations on genuinely empty databases to verify reproducibility.
3. Keep test databases isolated from developer and production databases.
4. Put transactions around complete service-layer business operations.
5. `flush()` sends SQL; `commit()` finalizes the transaction; rollback can undo flushed writes.
6. Prefer `LAZY` for relationships that are not always needed; inspect SQL before optimizing and consider targeted fetches for richer responses.
7. Disable OSIV for predictable service-layer persistence boundaries and map entities to DTOs within transactions.
8. Combine application-level validation with database constraints. Map expected integrity violations to safe, meaningful API responses.
9. A green unit test verifies its specific behavior, not untested concurrency or production deployment scenarios.
